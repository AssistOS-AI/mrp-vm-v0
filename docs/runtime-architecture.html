Implemented runtime

MRP-VM v0 runtime architecture

MRP-VM v0 is now implemented as a bounded execution machine with explicit planning, explicit state, explicit knowledge injection, and independent credibility assessment.

Architectural identity

MRP-VM v0 is specified as a runtime for local interpretive regimes rather than as a monolithic prompt wrapper. Tasks enter as natural language requests plus bounded context, then become a graph of SOP Lang declarations. Execution is mediated through native commands, external interpreters, family-based state, and auditable trace records.

The runtime-facing DS set lives in DS002 through DS033. These files define the implementation contract, and the repository now includes the corresponding runtime source tree, server adapter, declaration-style default KUs, Explainable Memory aspects, and tests.

Execution surfaces

Planning and control

DS002, DS003, DS006, and DS016 define graph compilation, topological execution, request entry, plan bootstrapping, epochs, and bounded repair behavior.

State and commands

DS002 defines families, variants, representative resolution, and declaration insertion; DS007 through DS012 define native command contracts. Within that surface, DS008 now defines `logic-eval` as a rewrite-orchestration helper rather than the final reasoning runtime, and its rewrite briefs may target either reasoning interpreter.

Knowledge and evaluation

DS005, DS011, DS012, DS017, DS019, and DS033 define bounded context, declaration-style prompt assets, deterministic-yet-explainable KB retrieval, governed aspect administration, independent candidate comparison, normalized failure handling, and evaluation strategy.

Hosting and chat

DS018, DS022, and DS033 define the top-level server/ adapter, SDK entry points, native APIs, SSE trace streaming, API-key-backed authority, and the five-page operational UI covering a compact conversation-first Chat surface, a dedicated Traceability workspace, a dedicated Cache workspace, a KB Browser, and tab-structured Settings. The current UI exposes syntax-highlighted SOP inspection, a left-to-right execution graph with horizontally distributed resizable layer columns, fixed-width centered node cards, and edges that follow adjusted column positions, synthetic workflow-boundary nodes for layer-0 planning start and final request result, a dedicated traceability Errors tab that preserves accumulated failure payloads and stacks, a fullscreen tabbed node inspector with a fixed header and scrolling body, explicit successful-request cache promotion and cache-entry deletion surfaces, pending-promotion cache inspection, issued-key-first authentication settings with popup-based key creation, compact model binding controls for both external LLM wrappers and internal stages such as logicGeneratorLLM and formatterLLM, a Memory settings tab for aspect editing, approval, and bounded log scanning, KB reindex controls, per-KU index-state visibility with aspect evidence, and stack-aware local server diagnostics for malformed requests and unexpected failures.

LLM routing

DS013, DS023, and DS032 define the Achilles-backed adapter boundary, `LLMAgent` usage, model tiers, task tags, request-scoped LLM capture, and the controlled shared-cache promotion path for wrapper interpreters.

Bounded reasoning

DS020, DS026, DS027, DS028, DS029, DS030, and DS031 define the external interpreter contract, the implemented reasoning interpreters, the document-scale planning interpreter, and the KU, demo, and evaluation guidance that lets planning choose them deliberately while keeping inserted plans and generated program surfaces tied to documented APIs.

Proposal-only surfaces

DS004 and DS021 are intentionally marked as proposal-only surfaces. They reserve architectural direction without being treated as immediate implementation baseline.

Implementation-ready decisions already fixed

Surface Consolidated rule
Interpreter outputs Commands return ordered lists of concrete variables plus metadata, not opaque result envelopes.
Knowledge retrieval kb defaults to symbolic Explainable Memory retrieval with inspectable aspect and lexical evidence; the naive symbolic path remains selectable, and LLMs stay reserved for governed induction and maintenance tasks. The admin surface now exposes approved, candidate, and scan-derived proposed aspects plus per-KU aspect evidence.
Memory naming analytic-memory is the canonical aggregation surface for v0.
Planning guidance Planning prompt guidance must come from KU-managed prompt assets rather than from large hardcoded prompt bodies, non-trivial plans should expose explicit solving or extraction, response-preparation, and final template-assembly phases instead of collapsing everything into one opaque response step, and canonical response-shape fixes such as wrapping a direct response interpreter into explicit preparation plus template-eval assembly should remain visible in the accepted SOP.
Reasoning routing Planning should prefer js-eval for exact deterministic sub-problems, route directly to HumanLikeReasoner only for bounded symbolic reasoning that still remains after that split, route directly to AdvancedReasoner for bounded advanced meta-reasoning, route directly to DocumentScalePlanner for bounded Markdown or JSON chunk workflows, and use logic-eval only when a rewrite brief is still needed. When js-eval is filling its declared target family, planner guidance should prefer an explicit final return. When template-eval is available, the final @response step should stay a deterministic template assembly rather than a direct reasoner call.
Server UI structure Chat stays conversation-first with a compact session status bar and a live trace-driven in-progress placeholder, while traceability, shared-versus-pending cache inspection, KB tuning, and tabbed settings remain on dedicated pages under server/ with one common general header navigation and templates and CSS stored outside JavaScript.

Current implementation boundary

The repository now contains the runtime tree under src/, including the dedicated src/interpreters/human-like-reasoner/, src/interpreters/advanced-reasoner/, and src/interpreters/document-scale-planner/ runtimes, the controlled shared LLM cache under data/cache/llm/, request-local pending capture artifacts under session storage, the top-level server and operational UI adapter under server/, the declaration-style default-KU assets under data/default/, the shared demo/eval catalog under eval/, and a modular native test suite under tests/. The current hosting surface distinguishes session origin, auth mode, effective role, explicit cache-promotion authority, API-key-backed authority, request-level verbose logging, and stack-aware local error diagnostics while keeping the SDK boundary intact.
